## The modes

### T5: Misfiled note or record: filed under one item, content only fits another

- **Status:** proven
- **Family:** record_reversal
- **Aimed at:** both
- **Clock trap:** no
- **Aliases:** misfiled note
- **Pooled misses:** Fable 53/170 (31%), Astra 81/170 (48%)
- **Loopholes:** L-record, L-absorb, L-threshold

A note, comment, letter or certificate is filed under item A, but what it says can only be about item B (dates, details or a description that A cannot meet). The default applies it to A as filed. Content-only misfiles bit Astra hard in some builds (ats, pathway) and not at all in others (spice 2.5.0, line-colour 1.4.0, timesheet 2.7.0). Measured here (build_evidence.py, 2026-10-15): final 10x2 pooled Fable 26/80, Astra 41/80; all stages Fable 53/170, Astra 81/170 (AMBIGUOUS/DEFECT units excluded); without unaudited >=90% units, final Fable 26/60, Astra 21/60. Audited GENUINE in 2 task(s). Status proven: audited GENUINE in 2 tasks; pooled final miss rate >= 0.2 with n >= 20 on fable, astra (unaudited >= 90% units excluded).

**Recipe**

- *record:* a complete note or comment that fits its filed key on a casual read
- *anchors:* two near-true details in the note that A cannot meet and B does (a date offset, a prior history), each checked against a record read for another purpose
- *withheld:* no sentence says the note was misfiled
- *dials:*
  - two near-true details: the ats 1.6.0 reader solved it, models still missed
  - an impossibility on A closes the 'apply to both' reading
- *conservation:* grade both A's and B's resulting values so 'apply to both' loses
- *shields:* none needed unless a filing rule exists; then scope it

**Proof obligations (authoring/validate.py)**

- uniqueness: only B meets every detail of the note
- ablation: each detail is necessary
- both-side grading: the union answer fails a check

**Hazards**

- an instruction-like note admitting a second destination: deck 2.5.0 N5 AMBIGUOUS (fixed 2.6.0)
- a one-day relayed count plus one likelihood is the thinnest point the audit accepted: ats 1.7.0 P6
- flat when it bites: ats 1.7.0 P6 was 20/20 the same wrong value

**What killed it**

- timesheet 2.7.0 P6 IT-log note: 0/15 on both models
- spice 2.5.0 P7 and line-colour 1.4.0 P5: 0/5 on both

**Trace signals**

- the user says a comment or attachment belongs to another item
- comment exports, certificate logs and correspondence filed by subject line

**Domains**

- recruiting and HR registers
- school administration
- deck and document review
- trading journals

**Example.** A resignation note filed under one candidate says notice was served 'three days after sitting our paper', which fits only the other candidate's sitting date.

### T8: Changed premise received before issue (filler only)

- **Status:** promising
- **Family:** revision_supersession
- **Aimed at:** fable
- **Clock trap:** no
- **Aliases:** changed premise before issue
- **Pooled misses:** Fable 12/55 (22%), Astra 0/55 (0%)
- **Loopholes:** L-record, L-shield

A letter received before the issue date changes a premise (a door must stay an escape door), so verdicts computed on the old premise are wrong. The default keeps the earlier verdicts. Measured on one task; the catalogue keeps it as a filler. Measured here (build_evidence.py, 2026-10-15): final 10x2 pooled Fable 7/30, Astra 0/40; all stages Fable 12/55, Astra 0/55 (AMBIGUOUS/DEFECT units excluded). Audited GENUINE in 1 task(s). - *record:* verdicts already worked out on the old premise
- *anchors:* a dated letter received before the issue and a drawing that ties it to the graded items
- *withheld:* no instruction says to re-check
- *dials:*
- *conservation:* the changed premise must flip graded verdicts
- *shields:* scope the PM's 'the change is X' sentence to its paragraph

**Proof obligations (authoring/validate.py)**

- dates: the change is received before the issue (executed)

**What killed it**

### T4: Already in hand: a 'still needed' item already held, shown by a technical bridge

- **Status:** promising
- **Family:** possession_state
- **Aimed at:** both
- **Clock trap:** no
- **Aliases:** S.inhand, already in hand
- **Pooled misses:** Fable 24/165 (15%), Astra 13/145 (9%)
- **Loopholes:** L-record, L-threshold

A rule orders or chases what is still needed, and a list says an item is outstanding. A first-hand record shows the item is already held, through a technical bridge the solver must make (a controller already running a known board; a vendor's job sheet for the scanned specimen). The default orders or chases the item. It dies when possession is stated. Measured here (build_evidence.py, 2026-10-15): final 10x2 pooled Fable 13/70, Astra 8/70; all stages Fable 24/165, Astra 13/145 (AMBIGUOUS/DEFECT units excluded). Audited GENUINE in 2 task(s). Status promising: short of proven: no model with pooled final rate >= 0.2 at n >= 20; not dead (some model above 0.05 or n < 20).

**Recipe**

- *record:* a still-needed list or chase line that names the item as outstanding
- *anchors:* two first-hand records whose technical content shows the item is held (a log line, a job sheet, an adviser's identification of the object)
- *withheld:* no sentence says the item arrived or is owned
- *dials:*
  - one semantic bridge per notch; two bridges were disclosed as the soft point in cnc 2.6.0
- *conservation:* grade the order or chase list as an exact set
- *shields:* scope any 'chase everything on the list' rule to items not yet received

**Proof obligations (authoring/validate.py)**

- uniqueness: exactly one listed item is shown held
- ablation: each bridge anchor is necessary (executed)
- no-statement grep: no line states possession

**Hazards**

- two semantic bridges were disclosed as the soft point: cnc 2.6.0 P5
- measured on two tasks only: cnc P5 (Fable) and psychopathy 2.4.0 P6 (Astra, templated T4 by its author)

**What killed it**

- possession stated outright: kibo 2.5.0/2.6.0 P5 commander scope, Fable 0/10
- possession inferred from one incidental remark: kibo 2.7.0 P5 0/5; blockprint P2 stock in the lock-up 0/10
- brightwater 1.4.0-1.6.0 P5 (T4 build): Fable 0/20 finals

**Trace signals**

- the user says 'I already have that' after a list is drafted
- shopping or procurement lists built from a template
- equipment or documents arriving by a side channel

**Domains**

- maker and workshop builds
- research data management
- web content launches
- budget card builds
